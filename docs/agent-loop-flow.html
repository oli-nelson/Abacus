Two state machines overlap

The green labels are AgentActivity values shown by the dashboard. The coding agent separately controls the Beads ticket status. Abacus keeps the host alive while the ticket is in_progress; closed, open, or blocked are all valid terminal signals that end the session.

An agent process exiting is never treated as completion by itself. Abacus reads the ticket again to resolve the exit/status race, then reopens and unassigns it if it is still in_progress.

Dashboard state vocabulary

STARTING
Application initialized; loop not yet claiming.
WAITING / IDLE
Checking for work / confirmed empty queue.
SYNCING / CLEANING
Pre-claim Beads pull / destructive workspace reset.
PREPARING
Claim held; issue branch is being selected.
WORKING
Agent host is live and supervised.
FINALIZING
Terminal ticket observed; run is ending.
RECOVERING / RETRYING
Repairing a claim / delaying another attempt.
STOPPED
Finite completion, shutdown, invariant failure, or halt.

Safety invariants

  • No ticket is claimed until the assigned Git workspace is present and clean. Cleanup intentionally discards tracked and untracked non-ignored changes.
  • Any failure after a successful claim attempts to return the ticket to open, clears its assignee, verifies the result, and pushes when configured.
  • Host cleanup is idempotent and targets only the tmux pane or direct child created by Abacus.
  • A failed recovery, unverified cleanup, or exhausted push retries prevents this loop from claiming more work.

Execution modes

  • continuous retries orchestration errors and keeps polling an empty queue.
  • --once processes at most one ticket; an empty first claim also completes it.
  • --drain returns to the queue after every ticket and stops when no ready ticket remains.
  • --ticket-timeout bounds one hosted run, then cleans the host and safely reopens work that remains in_progress.
  • --check never enters this chart: it exits immediately after non-mutating preflight.
