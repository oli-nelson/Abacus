01

Install the command-line tools

Abacus orchestrates existing CLIs. It does not replace Git, Beads, Claude Code, or tmux, and it supports macOS and Linux.

Required for this guide

Runtime tools

Git 2.55+ bd 1.2.2+ Claude Code 2.1.212+ tmux 3.6a+

Abacus also supports OpenCode and Codex, but the runnable examples below use Claude Code.

Building Abacus

.NET 10

The .NET 10.0.101 SDK is needed to build. A self-contained publish does not require .NET on the destination machine.

Verify the toolchain
git --version
bd version
claude --version
tmux -V
abacus --help
Build and publish Abacus
# Run in the Abacus source repository.
dotnet publish src/Abacus -c Release -o artifacts/publish
export PATH="$PWD/artifacts/publish:$PATH"
abacus --help
i

Health is the fastest diagnostic. Run abacus --health inside the target repository. It reports tool versions, Beads storage, server connectivity, no-git-ops, merge-slot status, Git worktrees, installed Abacus skills, and single-/multi-agent readiness.

02

Create a clean Git repository

Abacus treats assigned workspaces as disposable execution areas. Begin with a committed baseline and keep the primary checkout for administration.

New repository
mkdir -p ~/work/acme-widget
cd ~/work/acme-widget
git init -b main

printf '# Acme Widget\n' > README.md
git add README.md
git commit -m "Create project"

export REPO="$PWD"
export WORKTREES="$HOME/work/acme-widget-agents"
git status --short
!

Assigned worktrees must contain nothing precious. Before each claim, Abacus runs git reset --hard HEAD and git clean -fd when a workspace is dirty. Tracked edits and untracked, non-ignored files are discarded. Commit or move anything you need first.

  • The base branch exists and has a commit.
  • The administrative checkout is clean.
  • If the built-in merge process is unsuitable, repository instructions define a custom one.
  • Every future agent receives a distinct path.
03

Give every agent a worktree

A worktree is a second working directory attached to the same Git repository. Abacus never creates one for you and rejects duplicate resolved workspace paths.

Topology

Keep main out of the pool

Use $REPO to create issues, inspect health, and coordinate merges. Put disposable agent checkouts under $WORKTREES.

Branch ownership

Start detached

Abacus creates or reuses abacus/<issue-id> after claiming a ticket, so detached worktrees are a clean starting point.

Create two candidate agent worktrees
mkdir -p "$WORKTREES"
git -C "$REPO" worktree add --detach "$WORKTREES/alice" main
git -C "$REPO" worktree add --detach "$WORKTREES/bob" main
git -C "$REPO" worktree list --porcelain
i

Beads follows the Git common directory. Linked worktrees automatically discover the primary repository’s Beads workspace. Initialize Beads once from $REPO; do not initialize a separate database inside every worktree.

If Beads initialization adds project files or agent instructions after you create these worktrees, commit those files and recreate or update the detached worktrees to that commit before running agents.

04

Choose the Beads storage mode

Both modes use Dolt. “Embedded” means the engine runs in each bd process; “shared server” means concurrent clients connect to one SQL server and one database.

!

These are alternative initialization tracks—not consecutive commands. Do not run both initializers against the same existing .beads directory. If you outgrow embedded mode, use the Beads backup/restore migration rather than destructive reinitialization.

Track A · simplest

Embedded Dolt

Use for one Abacus agent. It needs no server and is the default Beads mode.

Initialize embedded
cd "$REPO"
bd init --non-interactive
bd config set no-git-ops false
bd dolt show --json
bd where
abacus --install-skills
abacus --health

Expect "embedded": true. Abacus permits exactly one configured agent with this storage mode.

Track B · concurrent

Shared Dolt server

Use for multiple Abacus agents. Beads manages one machine-wide server and isolates projects by database name.

Initialize shared server
cd "$REPO"
bd init --shared-server --non-interactive
bd config set no-git-ops false
bd dolt start
bd dolt status
bd dolt show --json
abacus --install-skills
bd merge-slot create
abacus --health

Expect "embedded": false, a reachable host/port, and "connection_ok": true.

!

Enable Git operations explicitly. Run bd config set no-git-ops false after initialization so the project does not inherit a global Beads setting that prevents Abacus agents from committing and merging. A Git remote is not required: Abacus explicitly authorizes local staging, commits, and merges in its agent prompt while forbidding git push.

Verify every worktree sees the same database

Identity check
bd -C "$WORKTREES/alice" dolt show --json
bd -C "$WORKTREES/bob" dolt show --json

For a multi-agent run, Abacus requires both outputs to identify the same reachable host, port, and database. Keep host spelling consistent—do not mix localhost and 127.0.0.1.

Using an externally managed Dolt server

If your team already owns a dolt sql-server, initialize Beads with explicit connection details. Abacus does not start or manage that external service.

External server example
bd init --server --external --non-interactive \
  --server-host 127.0.0.1 \
  --server-port 3307 \
  --server-user root \
  --database acme_widget
bd config set no-git-ops false
bd dolt test
bd dolt show --json

Create ready work

First issue
cd "$REPO"
bd create "Add a health endpoint" \
  --description "Add an HTTP health endpoint and cover it with tests." \
  --acceptance "The endpoint returns success and the test suite passes." \
  --type task \
  --priority 2 \
  --json

bd ready --json
✓

Optional merge guard. bd merge-slot create gives repository instructions a shared exclusive gate for serialized merges. Abacus excludes the gt:slot bead from claims. A missing slot produces a health warning, not a startup failure, because your repository may serialize merges another way.

05

Use the bundled agent skills

Abacus can install four focused agent skills into a repository. Installation makes them discoverable to compatible coding agents; it does not run them automatically or change the Beads database.

Install once from anywhere in the repository
cd "$REPO"
abacus --install-skills

# Installed under the Git root:
find .agents/skills -maxdepth 2 -name SKILL.md -print
i

Existing skill directories are protected. If a bundled skill already exists, Abacus names the affected skills and asks before replacing their complete directories. Declining leaves every skill unchanged; unrelated skills are never removed.

1 · Shape the work

Beads Planner

Turns a product or engineering concept into a reviewable epic, focused child issues, real blocking dependencies, priorities, labels, and testable acceptance criteria.

draft first approval before writes

2 · Check readiness

Beads Doctor

Audits issue content, fields, boundaries, labels, metadata, and graph direction for agent readiness. It reports evidence and proposed corrections before making repairs.

diagnose first confirm repairs

3 · Triage decisions

Beads Attention

Finds every abacus:needs-user-attention issue—including closed ones—and summarizes the decisions, access, outside actions, and failures that need a person.

read-only report highest impact first

4 · Check Git guidance

Git Check

Audits active agent instructions for misleading restrictions on local Git work while preserving legitimate limits on pushes and destructive operations.

instruction audit evidence first

Ask for the skill explicitly

Start a compatible coding-agent session in the repository and name the skill in your request. The dollar-prefixed form makes the intent unambiguous.

Plan a new body of work
Use $abacus-beads-planner to turn this concept into an execution-ready
Beads epic and issue graph:

Add offline synchronization to the desktop client. Separate protocol,
storage, UI, migration, and end-to-end verification work where useful.
Show me the proposed graph and execution waves before creating anything.

The planner inspects repository guidance, related issues, labels, and Beads conventions. It presents temporary issue keys, dependencies as “A depends on B,” acceptance criteria, and expected execution waves. Approve or revise that draft before it creates any durable issues.

Audit work before dispatch
Use $abacus-beads-doctor to audit epic ab-123 and all of its descendants
for agent readiness. Check scope, acceptance criteria, dependency direction,
parallelism, labels, priorities, and the ready set. Report findings first;
do not repair anything until I approve the proposed patch set.

The doctor classifies findings as agent-stoppers, graph errors, quality warnings, or suggestions. It complements the CLI’s database-health bd doctor; it is primarily a content and execution-readiness review. Approved repairs are read back and graph-checked afterward.

See what needs a person
Use $abacus-beads-attention to summarize everything that needs my attention.
Group the report into decisions, outside actions or access, blockers or
failures, and possibly stale requests. Tell me what to look at first.

The attention skill queries exactly the label used by the dashboard and reads each matching issue for context. It does not infer attention from blocked alone, and it does not clear labels or mutate tickets unless you explicitly ask after reviewing the report.

Audit agent-facing Git guidance
Use $abacus-git-check to audit this repository's active agent instructions
for incorrect local Git restrictions. Report the exact source and wording,
and distinguish local commit or merge limits from legitimate push limits.

Git Check follows the instruction hierarchy that actually applies in each workspace. It flags guidance that would prevent agents from completing Abacus's local branch workflow, but it does not weaken user instructions or grant push authority.

A practical cadence

  1. Plan. Turn the concept into a graph, review execution waves, then approve creation.
  2. Doctor. Audit the epic before agents start, approve precise repairs, and verify the resulting ready set.
  3. Check Git guidance. Confirm that active agent instructions allow the local commit and merge workflow while preserving any push restriction.
  4. Execute. Start Abacus with filters that select the approved work. The coding agents claim and complete individual tickets.
  5. Triage attention. Use the attention skill when the dashboard or desktop toast says a human decision or outside action is pending.
✓

The boundaries are intentional. The planner is not an implementation agent, the doctor does not silently rewrite plans or change lifecycle state, and the attention skill is not a general backlog review. Their reports keep durable planning, issue quality, execution, and human decisions separate.

06

Run one Claude Code agent

Claude Code runs interactively inside an Abacus-owned tmux pane. The Abacus dashboard stays in your current terminal while the full Claude interface lives in tmux.

  1. Create the tmux target. Abacus verifies an existing session and optional window; it never creates either.
  2. Check the disposable workspace. Use the Alice worktree or the clean primary checkout for a one-agent run.
  3. Start Abacus. The model is required; effort defaults to high.
i

Find model IDs with abacus --models. It groups IDs discovered from installed OpenCode and Codex CLIs. Claude Code exposes its available-model picker interactively through /model, so Abacus reports that guidance in the Claude Code group.

Single Claude agent
export SESSION=abacus-work
export WINDOW=agents
export MODEL=sonnet
export AGENT_WORKTREE="$WORKTREES/alice"

tmux new-session -d -s "$SESSION" -n "$WINDOW"
git -C "$AGENT_WORKTREE" status --short

abacus \
  --mode claude \
  --tmux-session "$SESSION" \
  --tmux-window "$WINDOW" \
  --tmux-layout tiled \
  --model "$MODEL" \
  --effort high \
  --notify attention \
  --notify-sound \
  -a alice "$AGENT_WORKTREE"

Attach to the Claude pane with tmux attach-session -t "$SESSION". Detach without stopping it using Ctrl-b, then d.

Optional · Claude Remote Control

Add --remote

In Claude mode, Abacus’s --remote switch keeps the session running locally and adds Claude’s --remote-control "<issue-id> • <issue-title>". You can then steer the same local session from claude.ai or the Claude mobile app.

Remotely steerable local session
abacus --mode claude --remote \
  --tmux-session "$SESSION" --tmux-window "$WINDOW" \
  --model "$MODEL" --effort high \
  --notify all --notify-sound \
  -a alice "$AGENT_WORKTREE"

This is not Claude’s cloud-execution --remote flag. Abacus maps its switch to Remote Control. The agent process, files, tools, and network access remain on your machine. Sign into Claude Code with a claude.ai subscription and accept workspace trust before relying on unattended startup; Team and Enterprise organizations may also need an administrator to enable Remote Control.

!

Ticket status ends the session. Claude must close the issue, reopen/unassign it for retry, or mark it blocked only after its code, commit, merge, and issue notes are complete. A process exit by itself is not success; Abacus reopens an issue that remains in_progress.

07

Scale to multiple agents

Each agent gets its own worktree and tmux pane, while every claim is made atomically against the same shared server-backed Beads database.

!

Embedded mode will be rejected. Multi-agent preflight succeeds only when every worktree reports the same reachable server host, port, and database.

!

Git operations must be enabled. Health and normal preflight check Beads no-git-ops. If it is enabled, Abacus exits before claiming work or starting an agent and reports bd config set no-git-ops false as the correction.

Create enough independent work
cd "$REPO"
bd create "Add health endpoint" --type task --priority 1 --json
bd create "Document health endpoint" --type task --priority 2 --json
bd ready --json

bd -C "$WORKTREES/alice" dolt show --json
bd -C "$WORKTREES/bob" dolt show --json
abacus --health
Two Claude agents
abacus \
  --mode claude \
  --tmux-session "$SESSION" \
  --tmux-window "$WINDOW" \
  --tmux-layout tiled \
  --model "$MODEL" \
  --effort high \
  --notify all \
  --notify-sound \
  -a alice "$WORKTREES/alice" \
  -a bob "$WORKTREES/bob"

Claim

Atomic

Each loop lists unassigned ready work, keeps the highest Beads priority, and uses the newest comment to break a tie. Before the atomic claim, Abacus skips a selected issue if bd show --children reports any unclosed direct child. Eligible issues are claimed with their own BEADS_ACTOR; lost races retry with bounded backoff and jitter.

Workspace

Isolated

Alice and Bob can never resolve to the same directory. Each ticket gets an abacus/<id> branch.

Queue

Shared

Both agents see ticket changes immediately through the shared Dolt server and cannot successfully claim the same issue.

08

Append repository-specific agent instructions

Keep Abacus’s built-in ticket workflow intact while adding instructions that apply to one repository or one invocation.

Repository

.abacus/append-prompt.md

Place this Markdown file at the root of an agent’s Git workspace. Abacus reads each workspace’s file during preflight and appends nonempty contents to that agent’s prompt.

Invocation

--append-agent-prompt

Pass one quoted, nonempty prompt fragment to apply it globally to every agent started by the invocation.

Use both prompt additions
mkdir -p "$REPO/.abacus"
cat > "$REPO/.abacus/append-prompt.md" <<'EOF'
Run the repository smoke-test checklist before completing the ticket.
EOF

abacus --mode claude \
  --tmux-session "$SESSION" --tmux-window "$WINDOW" \
  --model "$MODEL" \
  --append-agent-prompt "Keep the change narrowly scoped." \
  -a alice "$REPO"
i

Ordering is deterministic. The final prompt contains the built-in Abacus prompt first, the --append-agent-prompt value second, and .abacus/append-prompt.md last, separated by blank lines. Empty repository files are ignored; an empty command-line value is rejected.

Follow the latest Beads comments

New ticket claims start enabled. Press Shift-Tab to pause or resume claims across all agents. Tickets that are already active keep running; agents at the next claim boundary display PAUSED, and the header always shows the current claim state.

The dashboard polls Beads in the same five-second cycle used for user-attention detection, then places the newest comments at the very bottom, newest first. It shows up to 8 entries by default. Each entry puts the issue ID, a width-aware truncated issue title, and the comment author on a header line. The comment appears on the indented line beneath it, giving the text nearly the full terminal width before truncation. Newlines and repeated whitespace within the comment are collapsed onto that one body line.

10

Ask for user attention without blocking

Attention is a persistent Beads label, separate from ticket status. An agent can request a decision and continue working, or combine the label with blocked when it cannot proceed.

Raise, resolve, and block
# Ask for awareness or a decision while continuing when possible.
bd comment <issue-id> "Choose the public endpoint name."
bd update <issue-id> --add-label abacus:needs-user-attention --json

# Record your response as a comment, then remove the persistent alert.
abacus --resolve <issue-id> "Approved: use public-api"

# Or remove the alert without adding a response comment.
abacus --resolve <issue-id>

# Resolve, reopen, and unassign the ticket so an agent can claim it again.
abacus --resolve <issue-id> "Approved: use public-api" --reopen

# List every ticket still carrying the attention label.
abacus --list-user-attention

# Delete local abacus/* branches for closed tickets.
abacus --prune-closed-branches

# If no work can continue, also mark the ticket blocked.
bd comment <issue-id> "Waiting for the API name decision."
bd update <issue-id> --status blocked --json

Resolve with context

Leave a durable response

When you supply a quoted message, Abacus first adds that exact message as a Beads comment, then removes the attention label. Add --reopen to make that same update set the ticket to open and clear its assignee. If the comment fails, the label and status stay in place.

Standalone command

No agent run required

Run the command from the current Beads project. It does not require a model, worktree, tmux session, or agent harness, and it prints a concise confirmation instead of raw Beads JSON.

  • Abacus polls the attention label about every five seconds.
  • The dashboard shows issue ID and title, including closed issues.
  • The alert persists until the label is removed.
  • Desktop notices deduplicate by issue ID while the label remains.
  • Remove and later restore the label to notify again.
  • Persistent recovery failures also occupy the attention panel.
i

Attention alerts and comments have separate views. The attention panel and desktop notification carry only the issue ID and title. Recent decision requests and responses can appear in the dashboard’s latest-comments log; use bd show <issue-id> when you need the complete, untruncated discussion.

Control which issues enter the pool

Dispatch filters are global to the Abacus run and are passed literally to every fresh claim and same-agent resume lookup.

ArgumentRepeat?Effect
--label <label>YesRequire the label. Repeating it requires all supplied labels.
--exclude-label <label>YesReject issues carrying any supplied excluded label.
--type <types>NoPass one Beads type filter; comma-separated values such as bug,task are allowed.
--priority <0…4>NoMatch one exact priority: 0 is highest, 4 is lowest.
Filtered multi-agent run
abacus --mode claude \
  --tmux-session "$SESSION" --tmux-window "$WINDOW" \
  --model "$MODEL" \
  --label abacus-ready \
  --label team:platform \
  --exclude-label needs-human \
  --exclude-label on-hold \
  --type bug,task \
  --priority 1 \
  -a alice "$WORKTREES/alice" \
  -a bob "$WORKTREES/bob"
✓

Beads still decides readiness. Dependencies and ticket status continue to govern bd ready. Abacus additionally skips candidates with unclosed direct children and always adds --exclude-label gt:slot, so neither unfinished parents nor the merge coordination bead become coding work.

Filter values must be nonempty and contain no whitespace. --type and --priority may each appear only once. There are no per-agent filter sets in one invocation.

Notification examples

macOS

osascript

Abacus invokes /usr/bin/osascript and uses Hero and Basso as its positive and negative sounds. Notification text is supplied through environment variables rather than interpolated into AppleScript.

Linux

notify-send

Install notify-send and run within a graphical notification session. Abacus passes title/body as separate process arguments and requests the standard complete and dialog-warning sounds; support depends on the active notification daemon and sound theme.

i

Sound is opt-in. --notify-sound requires attention or all. Closed tickets and fully successful runs use a positive sound. Attention, persistent failures, reopened, blocked, or interrupted outcomes and run summaries containing any of those outcomes use a negative sound. When desktop delivery fails, Abacus may emit a terminal bell. Delivery is best effort, appears only in verbose diagnostics when unavailable, and never changes orchestration outcomes.

Notification text can expose issue titles and operational errors on the desktop. Persistent errors may contain an issue ID, path, pane/process location, or exception message. Notes, prompts, source code, and command output are not intentionally included.

Operate and stop safely

Abacus is designed to make terminal states explicit and to return unfinished claims to the queue when a process disappears or the orchestrator stops.

Continuous

Default

Wait forever, poll every five seconds, and retry transient orchestration failures.

Finite

--once / --drain

Process one ticket per agent, or empty the ready queue, then print a summary and exit.

Validation

--check

Run preflight without cleaning, claiming, creating panes, or printing a run summary.

Useful operator commands
abacus --health
bd ready --json
bd list --all
bd show <issue-id> --json
tmux list-panes -t "$SESSION" -F '#{pane_id} #{pane_title}'
tmux attach-session -t "$SESSION"
  1. Stop Abacus with Ctrl-C. It interrupts active panes, checks ticket state, and attempts to reopen work still marked in_progress.
  2. Read the run summary. Confirm closed, reopened, blocked, and interrupted counts and inspect any persistent attention section.
  3. Remove tmux yourself. Abacus owns its panes, not your session or window: tmux kill-session -t "$SESSION".
  4. Inspect worktrees before reuse. Agents are responsible for committing and following the repository’s serialized merge workflow.
